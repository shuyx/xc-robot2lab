# XC-Robot 技术方案优先级重排与一期 P0 方案详审

> 本文档基于《项目知识库总览》《报告 A 双 X86》《报告 B 双 RDK》《揭榜挂帅申报书》《联合研发中心框架协议》《合作任务书规划》六份资料的横向对齐，聚焦三件事：
>
> 1. **两份技术分析报告的盲区识别与修正**
> 2. **对照揭榜挂帅考核指标的再评估**
> 3. **基于用户一期目标（实物落地 + 稳定可复现 + 点位移动/抓取/交互）重排优先级、详审最高优先级方案**

## 一、一期目标的三重对齐

### 1.1 用户目标锚定

> **原话**："让机器人具备稳定、可复现、可靠的能力，能够实现不同点位间的移动、抓取，并完成简单交互后的任务处理。"

拆解为可验证的三条底线：

| 能力项 | 判据 | 最低门槛 |
|--------|------|----------|
| 稳定 | 相同条件下连续执行不崩溃 | 连续 4 小时压力测试不死机 |
| 可复现 | 同一任务多次执行成功率一致 | 10 次抓取 ≥ 8 次成功 |
| 简单交互闭环 | 语音 → 导航 → 抓取 → 放置 → 反馈 | 一句话指令 Demo 跑通 |

**这是本期工程目标的红线**。所有技术讨论与资源分配都要先过这三条。

### 1.2 与揭榜挂帅阶段对齐

揭榜挂帅项目实施周期 **2025-08 至 2027-07**（24 个月），分四阶段：

| 阶段 | 月数 | 任务 | 目标达成度 |
|------|------|------|-----------|
| 阶段一 | 0–6 月 | 系统总体方案设计 | 方案冻结（已完成） |
| **阶段二** | **6–18 月** | **关键技术突破与模块研发** | **关键指标达目标值 80%** |
| 阶段三 | 18–24 月 | 系统集成与场景验证 | 自测全指标通过 |
| 阶段四 | 24 月内 | 第三方检测与成果交付 | CNAS 检测通过 |

**当前（2026-04）处于阶段二早期**，对应的考核要求不是"指标 100%"而是 **"各指标达到最终指标 80% 以上"**。这是关键——很多问题不必一次到位。

### 1.3 与合作任务书 RD1–RD4 阶段对齐

| 阶段 | 时间 | 状态 | 主要内容 |
|------|------|:----:|----------|
| RD1 方案设计与技术冻结 | 2026-03 → 2026-04 | 收尾 | 需求澄清、方案冻结、关键器件 BOM（BOM v2.1 已冻结） |
| **RD2 样机研发与系统集成** | **2026-05 → 2026-08** | **即将进入** | **本体、感知、控制、升降、能源核心模块开发 + 联调** |
| RD3 调试验证与场景优化 | 2026-09 → 2026-10 | — | 实验室联调、典型场景测试、问题修复 |
| RD4 验收交付与成果固化 | 2026-11 → 2026-12 | — | 验收、文档、成果包 |

**本期 = RD2 + RD3 首月（5 个月工程窗口）**。这是本文档所有建议的时间边界。

### 1.4 一期边界定义

| 必做（P0/P1） | 本期砍掉（P2 / 二期） |

## 二、报告 A / B 的技术分析盲区识别

### 2.1 报告 A（双 X86 方案）的 6 处不足

#### 2.1.1 ❗ "单臂重复精度 ±0.1 mm 物理做不到"表述有验收风险

**原文**（§1.2 第 7 条、§2.3 表格）：
> "准直驱臂的 3C 精度悖论：达妙 DM 系列关节重复精度物理极限约 0.1–1 mm……无法靠开环定位打赢 SCARA"
> "❌ 物理极限约 0.3–1 mm | 必须靠力控柔顺装配补足"

**问题**：揭榜挂帅验收对"单臂重复定位精度 ≤±0.1 mm"是**硬指标**（申报书 §一.3、§四.1）。报告 A 直接说"物理做不到"，对验收答辩极其不利。

**正确拆解**：
- **自由空间关节回位精度** ≤ 0.1 mm —— 9:1 行星 QDD 物理极限 0.3–1 mm，**这一层确实做不到**
- **接触装配精度** ≤ 0.1 mm —— 视觉粗定位（±5 mm）+ 力控接触柔顺（±0.1 N 的力反馈微调）**可以达到**
- **揭榜挂帅验收场景 = 上下料/插拔/装配/锁付，全部是接触任务**，所以验收层面的 ±0.1 mm **是可实现的**

**修正表述**：不说"物理做不到"，说"靠关节层做不到，靠接触层 + 视觉/力控闭环可以达到"——路径变化，承诺不变。

#### 2.1.2 ❗ 多模态感知融合（激光+RGBD+鱼眼+力觉）讨论严重不足

**揭榜挂帅申报书 §二.1.难点一** 把"**几何—语义—力觉三层融合**"作为**核心创新点**（§二.3.创新点一），要求"激光雷达 SLAM + RGB-D 视觉 + 全景鱼眼 + 六维力觉在 ROS 2 体系中实现高精度标定、时空同步、多源数据对齐与统一接口输出"。

**报告 A 覆盖情况**：
- §4.2 只讨论激光 SLAM + AprilTag → 单模态导航级
- §4.4 只讨论手眼标定 → 单模态视觉 + 机械臂
- **没有系统章节讨论"四模态 + 语义 + 力觉融合 + 统一场景表征"**
- 头部鱼眼、六维力在报告中近乎缺席

**这是第三方检测时的主要扣分项**——检测报告会明确要求 "多模态融合模型可输出语义化场景表征（工件、工位、工具状态）"。

#### 2.1.3 ❗ 柔性任务调度（行为树 + FSM + 异常重规划）系统讨论缺失

**揭榜挂帅申报书 §二.1.难点二、§二.3.创新点二** 把"**行为树 + 状态机 + 语义状态感知 + 任务重规划**"作为**第二大核心创新**。

**报告 A 的 §3.1 只给了一行**："Skill 编排 / Scenario FSM / VLA Agent"，无任何工程细节。

**缺失的讨论点**：
- BT 与 FSM 的分工（BT 做流程、FSM 做关键动作状态监视）
- 任务异常触发条件（抓取失败/物料缺失/工位占用）
- 重规划的执行路径（谁触发、谁执行、回退栈）
- 语义状态感知如何接入（从感知 → 调度层的消息协议）

**影响**："任务柔性化"是揭榜挂帅三大核心创新之一，若无工程化落地，创新点专利布局和第三方检测都有隐患。

#### 2.1.4 ⚠️ 升降轴 8-DOF 统一规划对一期过于激进

**报告 A §4.3** 强推"升降轴 URDF prismatic + arm_torso 8-DOF MoveIt 统一规划组"，批评状态机做法"会局部最优"。

**问题**：
- 报告自己写 "8-DOF 组求解时间 < 200 ms"——这是乐观估计，OMPL 在高维空间常常卡到 500 ms 以上甚至失败
- 升降中的动力学参数随 z 变化（M(q) 依赖构型），Pinocchio 每步重算加上 8-DOF 规划，RD2 阶段工程复杂度过高
- TIAGo 参考案例是 10+ 年工程打磨的成熟平台，我们一期 5 个月做不到同等水平

**RD2 阶段应选**：**先做"升降到位 → 规划臂"的状态机**，虽然在狭窄工位有局部最优问题，但 **3C 工位 SMT 料盘和办公递送场景 99% 用不到"边升降边伸臂"**。8-DOF 统一规划放到 P1 或二期。

#### 2.1.5 ⚠️ MoveIt Servo 在接触任务上的适用性被高估

**报告 A §3.1 控制链路** 把 MoveIt Servo 放在通用 Servo 层上，隐含覆盖所有场景。

**实际**：MoveIt Servo 擅长"轨迹跟踪 + 奇异性处理"（用于遥操、视觉伺服跟踪），但**接触/装配任务不应走 Servo**：
- Servo 是位置级流式指令，没有内置力反馈闭环
- 接触瞬间的目标姿态语义是"力保持 + 小位移"，不是"速度跟踪"
- 工业机械臂的接触任务都走**独立的笛卡尔阻抗 / 导纳控制栈**（Franka libfranka、UR ForceMode）

**正确分工**：
| 场景 | 控制层 |
|------|--------|
| 自由空间 P2P | MoveIt OMPL → JTC（简单） 或 Servo（高级） |
| 视觉伺服跟踪 | MoveIt Servo |
| **接触/装配** | **独立的笛卡尔阻抗控制器**（不走 Servo） |

**一期建议**：自由空间走 JTC，接触任务走**简化阻抗控制**（关节级 + 末端虚拟弹簧），不在本期做 Cartesian impedance 完整工程化。

#### 2.1.6 ⚠️ 动力学标定 + 摩擦辨识 "W1 完成"过于乐观

**报告 A §4.1** 列的 5 步路径把动力学参数实测 + 摩擦辨识压在 W1，但：
- 扭摆法 / 两点悬挂法 **需要专用工装**（夹具、摆杆、激光位移传感器），工装加工周期 2–3 周
- 摩擦正弦扫频需要 **关节级驱动 + bag 记录**，但 MIT 模式 effort 接口尚未改好（鸡生蛋问题）
- Stribeck 离线拟合需要数据后处理代码，要写要调

**现实估计**：
- W1：工装设计 + 外协加工下单
- W2：扭摆法 + 悬挂法首关节测试
- W3：全关节测试 + 摩擦扫频
- W4：参数入库 + MuJoCo 回放验证

**4 周**才是真实数字，不是 1 周。

### 2.2 报告 B（双 RDK 方案）的 4 处不足

#### 2.2.1 ❗ R52 硬实时优势在本阶段大概率用不到

**报告 B §1.2 第 2 条、§3.2** 把"R52 × 4 硬实时核跑 1 kHz 控制"作为**核心卖点**。

**但报告 B 自己在 §4.3 坑 #3 明确承认**：
> "如果地瓜原厂支持到位，W2–W3 可以完成 R52 上的 1 kHz 主循环；**如果原厂支持不到位，降级方案：R52 固件暂不开发，用 Ubuntu A78AE + PREEMPT_RT 跑 1 kHz，与 X86 方案等效**"

**现实**：
- RDK S100 于 2025 年底才正式出货，R52 + Pinocchio codegen + CAN-FD 的官方工程化案例几乎没有
- 地瓜 FAE 对 R52 裸机 + 实时控制栈的支持深度未知
- 团队无 Cortex-R 裸机经验，学习曲线陡

**结论**：R52 硬实时路径在一期 5 个月内大概率走不通 → 降级 → 与 X86 方案等效 → **RDK 方案丧失关键差异化优势，只剩国产化 + BPU 算力**。

#### 2.2.2 ❗ aarch64 迁移 + 10 个坑的工作量被低估

**报告 B §4** 列了 10 个坑，每个坑按 1–5 天估算，合计时间预算就已 **15–25 人天**，再加上 **OpenArmX_xc 代码全量交叉编译 + 修复**，保守估计 **W1–W2 完全填满**。

**但 W1–W2 同期还要**：
- URDF 动力学标定（4 周）
- 摩擦辨识（2 周）
- 底盘导航调试
- 手眼标定

**时间冲突**：RDK 迁移 + 主线研发任务在 2 个月窗口内并行跑，团队没有这个资源。

#### 2.2.3 ⚠️ VLA 推理算力优势在本期不构成差异化

**报告 B 主要差异化卖点**：BPU 128 TOPS 跑 VLA（π0、RDT）。

**核对合作任务书 + 申报书**：
- 揭榜挂帅申报书**没有承诺 VLA 能力**，核心是"多模态感知 + 柔性调度"
- 合作任务书把"VLA/ER 模型适配"列为 **RES08 技术储备类**（按需启动，非必做）
- 客户 Demo 需求（语音 → 点位 → 抓取 → 放置）用 Skill + 关键词路由即可，**不需要 VLA**

**结论**：BPU 128 TOPS 的优势在本期用不上，RDK 方案的真实差异化窗口要等到二期"有客户明确要 VLA"时才开启。

#### 2.2.4 ⚠️ "W1 双线并行"推荐存在资源矛盾

**报告 B §十 推荐** 的混合路线：W1 双机双线跑 RDK + X86，W1 末评审选一栈。

**矛盾**：
- 报告自己估"两个月 Demo 达成概率：X86 85% vs RDK 60%"
- 双线等于 **资源稀释 30%**（双份装机、双份调试、双份 rosdep），Demo 成功率反而下降
- "W1 止损点"判定标准（Nav2/MoveIt 至少一个跑起来）过于宽泛，实际可能"跑是跑起来但不稳定"——难决策

**更好的做法**：一期直接选 X86（证据：BOM v2.1 已切 X86，代码已基于 Ubuntu 22.04 x86-64 开发），**RDK 方案延后到二期重评**，届时有：
- RDK S100 官方生态 1 年成熟期
- X86 方案的 Demo 数据可以做横向对比
- 客户国产化需求是否真实落地有更清晰的判断

### 3.2 "单臂重复精度 ±0.1 mm" 的分层承诺

这是**最容易在答辩和检测时出事**的指标，必须用分层方式正面回应：

```
承诺解读
  ├─ 自由空间关节回位精度
  │    物理约束：9:1 行星减速 + MIT 模式
  │    物理极限：0.3–1 mm
  │    项目承诺：通过力矩前馈 + 摩擦补偿做到 0.3–0.5 mm（80% 目标达成）
  │
  └─ 接触装配精度（验收场景）
       物理路径：视觉粗定位（±5 mm） + 接触柔顺（力反馈）+ 视觉/力觉微调
       物理极限：取决于传感器精度
       项目承诺：在 3C 装配、插拔、锁付场景达 ±0.1 mm
       证据：Franka/UR 等工业协作臂都靠这条路径达成 μm 级装配
```

**答辩话术**：
> "我们的 ±0.1 mm 不是关节伺服层的承诺，是**任务完成层的承诺**——在抓取/装配/插拔等接触任务中，通过'视觉粗定位 + 力控柔顺 + 在线校准'的闭环实现。这是工业协作机器人的主流路径，Franka、UR 均如此。"

## 四、优先级重排

### 4.1 重排原则

1. **阻塞项优先**：不解决则 Demo 跑不通的 → P0
2. **验收硬指标优先**：检测报告扣分项 → P0 或 P1
3. **架构级覆盖优先**：两份报告的共同盲区 #1/#2 先搭架子，不必填满 → P0
4. **完备性追求延后**：没有客户实际需求时砍掉 → P2
5. **路径替代可用时延后**：如 Servo→JTC、8-DOF→状态机、热插拔→单电池+UPS → P1/P2

## 五、P0 方案详细审查

### 5.1 P0-1：机械臂关节级稳定控制（7 周）

#### 5.1.1 问题本质

报告 A §4.1 已给出根因分析：JTC 100 Hz + position-only + 无前馈 + QDD 9:1 行星 = 必然抖动。但报告 A 的 5 步路径对一期过于激进。**本期只做最小可行集**。

#### 5.1.2 最小可行集：砍掉什么、保留什么

| 报告 A §4.1 提出的步骤 | 一期决策 | 理由 |
|----------------------|---------|------|
| Step 1 动力学参数实测 | **保留** | 重力补偿必备 |
| Step 2 摩擦辨识 | **保留** | 低速不抖必备 |
| Step 3 compensated_impedance_controller | **保留** | 核心控制器 |
| Step 4 Ruckig 在线整形 | **保留** | 防顿挫必备 |
| Step 5 MoveIt Servo | **砍掉（延后 P2）** | 自由空间用 JTC 足够，接触任务走独立栈 |

**新增**：
- **1 kHz 退让为 500 Hz**（先达目标 + PREEMPT_RT 稳定）
- **command_interface: effort** 接口必须改（MIT 模式基础）

#### 5.1.3 5 个里程碑

```
M1（2 周）：重力补偿 —— 不下沉
  输入：CAD 模型 + 实测质量
  工具：扭摆法 + 两点悬挂法（需工装）
  产出：
    • inertials.yaml（实测值替换 CAD 估值）
    • Pinocchio RNEA 封装 pinocchio_dyn_wrapper.hpp
    • compensated_impedance_controller 第 1 版（只加重力项）
  验收：关节悬空静止 60 s，漂移 < 0.05 rad（放宽自报告 A 的 0.01 rad）
  风险：工装加工延期 → 提前 2 周下单
```

```
M2（2 周）：摩擦补偿 —— 低速不抖
  输入：M1 完成
  工具：单关节正弦扫频（0.1–1 rad/s × 10 点）+ rosbag + 离线拟合
  产出：
    • friction.yaml（Stribeck 三参数 fc/fs/fv）
    • controller 第 2 版（加摩擦前馈项）
  验收：关节 0.1 rad/s 低速运动无粘滑，抖动振幅 < 0.01 rad
  风险：effort 接口未改完 → M2 与 M4 并行，先读 IMU 估速度
```

```
M3（1 周）：Ruckig 整形 —— 防顿挫

  工具：Ruckig Type V 在线整形，250 µs 周期
  产出：
    • ruckig_smoother.cpp
    • controller 集成，目标 500 Hz jerk-limited 轨迹
  验收：末端绘圆 10 cm，路径偏差 < 5 mm（放宽自报告 A 的 2 mm）
  风险：Ruckig 与 controller 线程同步问题 → 用 shared_ptr + mutex
```

```
M4（1 周）：PREEMPT_RT + 500 Hz + effort 接口
  输入：可与 M1–M3 并行
  工作：
    • Ubuntu 22.04 内核切 PREEMPT_RT（参考 atom01_deploy）
    • isolcpus 隔离专核
    • chrt -f 80 控制线程
    • ros2_controllers.yaml: update_rate 100 → 500
    • command_interfaces: [position] → [position, velocity, effort]
  验收：cyclictest -t 4 -p 80 -i 200 -D 10m，P99 < 100 µs
  风险：PREEMPT_RT 在 Intel Mini PC 上硬件兼容性 → W1 验证
```

```
M5（1 周）：OMPL 规划 + JTC 执行（不上 Servo）
  输入：M1–M4 完成
  工作：
    • MoveIt OMPL 规划典型 P2P 路径
    • JTC 执行（用 M3 Ruckig 输出做轨迹平滑）
    • 单臂从 home → 抓取位 → 放置位
  验收：单臂 "起点 → 终点" 执行 20 次，位置偏差 < 5 mm，无顿挫
  风险：规划失败率 > 10% → OMPL 参数调整（RRT* → RRTConnect）
```

**7 周总验收**：关节悬空静止不下沉 + 低速不抖 + 手动拖动无阶跃 + 末端绘圆 + P2P 规划 20 次全成功。

#### 5.1.4 砍掉 MoveIt Servo 的代价
