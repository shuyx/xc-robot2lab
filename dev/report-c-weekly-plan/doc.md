# W1（2026-04-16 → 04-22）"路线验证周"

## 1. 为什么这么做
方案选型（X86 vs RDK）是整个 2 个月研发的**上游决策**。如果错了，后 7 周都是沉没成本。唯一的正确做法是**W1 同步双线快速验证**，用实证数据在 W1 周末拍板，而不是基于直觉或 PPT。这周所有其他活动都以"不阻塞路线决策"为原则。

## 2. 技术难点与技术路线
- **难点 1**：双路主控（X86 + RDK）要在同一周内都跑起来 Nav2 + MoveIt 2 Demo
- **难点 2**：RDK 方案的 aarch64 包兼容性未知，TogetheROS 与上游 Humble 的 ABI 冲突未知
- **难点 3**：PREEMPT_RT 在两个平台上都要验证（cyclictest）
- **难点 4**：客户场景未锁定，数据标准无法开始建立

**技术路线**：
- **X86 栈**：Intel NUC i7 + Ubuntu 22.04.4 LTS + PREEMPT_RT 6.1（mainline）+ ros-humble-moveit + ros-humble-nav2，直接 apt 装
- **RDK 栈**：RDK S100 + SDK v4.0.3（含 rt43 内核）+ TogetheROS.Bot，先 `ros2 run demo_nodes_cpp talker/listener`，再加 Nav2 / MoveIt

## 3. 具体做法（按天拆）

- 学生 γ 开始场景文档：和客户电话 1 小时，整理 "v1 场景" 草案

**Day 3（周一 04-20）**

# W2（04-23 → 04-29）"底座周"

## 1. 为什么这么做
上周确定了主控路线，这周要把"能跑通 Demo"升级为"能跑通**自己的机器**"——部署实时内核、跑通 Robstride 真实臂的底层 CAN 通信、跑通 ZLAC8015D 真实底盘的闭环、实测 URDF 动力学参数。这些都是后续所有高级功能的**底座**。

## 2. 技术难点与技术路线

- **难点 1：URDF 动力学参数实测**。当前 `inertials.yaml` 来自 CAD 估算，误差 10–20%，直接导致所有前馈补偿失效。
- **难点 2：Robstride CAN-FD 通信稳定性**。openarm_can 默认是 Damiao MIT 协议，需要适配 Robstride 的 MIT 实现（两者协议略有差异）
- **难点 3：底盘里程计精度**。当前漂移 > 50 cm/10 m，需要重新实测轮径/轴距 + 融合 IMU
- **难点 4：学生对 URDF 实测无经验**，必须顾问现场带做

**技术路线**：
- URDF 标定：逐关节悬挂 → 质量 → 重心（两点悬挂法）→ 惯量（扭摆法）
- CAN 驱动：fork openarm_can，改 `damiao_motor_driver.cpp` 为 Robstride 版本
- 底盘驱动：SocketCAN + CANopen，抄 atom01_deploy 的 zlac8015d 实现
- IMU 融合：robot_localization EKF，融合轮式 + ROSEB43i 内建 IMU

## 3. 具体做法

**Day 1（周四 04-23）**
- 学生 α + 顾问：**URDF 实测 SOP 走一遍**。逐关节悬挂、悬挂点测重心、输出到 `inertials_measured.yaml`。顾问现场督导，学生跟做。
- 学生 β：编译底盘 chassis_driver，用 `candump` 测试 ZLAC8015D 响应
- 学生 γ：头部 RDK X5 刷系统（或头部 mini PC 装 Ubuntu），装基础 ROS 2

**Day 2（周五 04-24）**
- 学生 α：继续标定右臂，验收标定结果（质量误差 < 5%）
- 学生 β：底盘速度环闭环，下发 0.5 m/s 指令，实测误差 < 3%
- 学生 γ：继续头部启动任务，目标是 ROS 2 节点可通信

**Day 3（周一 04-27）**
- 学生 α：写 `friction.yaml` 摩擦辨识脚本。用 Robstride 电流反馈做单关节正弦扫频 0.1–1 rad/s
- 学生 β：轮式里程计精度测试，10 m 直线漂移目标 < 10 cm（若不达标就调参）
- 学生 γ：头部装 Porcupine 唤醒词；准备 W3 的 ASR 任务

**Day 4（周二 04-28）**
- 学生 α：摩擦参数离线拟合（Stribeck 曲线），写入 `friction.yaml`
- 学生 β：robot_localization EKF 配置，融合 IMU，实测闭环精度
- 学生 γ：人脸识别模型准备（RetinaFace + ArcFace），收集 5 个员工样本

**Day 5（周三 04-29）**
- 全员 M1 里程碑验收
- 所有产出汇总、提交 `W2_summary.md`

## 4. 能力支持
- **人**：顾问 W2 现场至少 3 天；三个学生全职

# W3（04-30 → 05-06）"流控制周" ⭐ M2

## 1. 为什么这么做
前两周的铺垫都是为了这一周：**让机械臂从"能动"变成"丝滑地动"**。这是整个 2 个月最关键的技术突破周——如果 W3 结束还是 100 Hz 离散轨迹控制 + 无前馈，后续所有工作都是空中楼阁。

## 2. 技术难点与技术路线

- **难点 1：MoveIt Servo 的配置与接入**。OpenArm 原版没有 Servo 配置，要从 0 写 `servo_config.yaml`
- **难点 2：500 Hz + PREEMPT_RT 的实测可行性**。理论可行，但实际取决于 CAN-FD 驱动的调度延迟
- **难点 3：前馈补偿控制器（compensated_impedance_controller）的编写**。要把 Pinocchio + Ruckig + ros2_control 串起来
- **难点 4：底盘 SLAM 建图质量**。一次性建图机会只有一次，做不好要重来

**技术路线**：
- 控制频率：`controller_manager::update_rate` 从 100 改到 1000，实测 cyclictest + ros2 topic hz 验证

## 2. 技术难点与技术路线

- **难点 1：关节空间阻抗控制的参数调校**。没有真实力传感器，完全靠电流反求力矩，噪声大

- Docking：用 `apriltag_ros` + `nav2_docking_server` 扩展点，写自定义 `AprilTagChargingDock` 类

# W7（05-28 → 06-03）"磨刀周" ⭐ M6

## 1. 为什么这么做
W6 跑通了整机但成功率可能只有 60%。本周的唯一目标是**把成功率从 60% 打到 90%**。这不是做新功能——是专项稳定性工程。两种做法：① 找失败原因一个个解决 ② 加鲁棒性（重试、超时、fallback）。

## 2. 技术难点与技术路线

- **难点 1：Failure mode 分析的系统性**
- **难点 2：重试策略不能引入新问题**（例如抓取失败后再抓一次可能把零件撞飞）
- **难点 3：长时运行的漂移问题**（2 小时后 TF 累积误差、内存泄漏）
- **难点 4：交互体验打磨**（表情、语音反馈、延迟感知）

**技术路线**：
- Failure mode：建 Grafana dashboard 自动统计每步失败率
- 重试：在 BT 中加 Retry + Timeout 节点
- 漂移：定期回 home 触发一次完整校准
- 打磨：录制用户感知视频，找出"卡顿/迟疑"时刻

## 3. 具体做法

**Day 1（周四 05-28）**
- 连续 50 次测试（Session 1），记录每次失败的 step
- 生成失败分布饼图

**Day 2（周五 05-29）**
- 针对 top 3 失败 mode 做专项修复
- 加入 BT 重试节点

**Day 3（周一 06-01）**
- 连续 50 次测试（Session 2），目标成功率 > 80%
- 针对剩余 failure mode 继续修

**Day 4（周二 06-02）**
- 连续 50 次测试（Session 3），目标成功率 > 90%
- 交互体验打磨（表情、延迟、语音反馈）

**Day 5（周三 06-03）M6 里程碑验收**

## 4. 能力支持

- **人**：项目负责人现场 50% 精力
- **设备**：Grafana + Loki 看板、录像设备
